## Part 2 — answers

**1. What does `shader_type` decide?**
`shader_type` decides which nodes the shader can be used on and which built-in variables it can use. Line 1 of `hit_flash.gdshader` is `canvas_item`, so it is a 2D shader. Line 1 of `brick_surface.gdshader` and of `hint_experiment.gdshader` is `spatial`, so they are 3D shaders that go through 3D lighting.

**2. Which processor functions did you write, and when does each run? What would change if the colour line moved into `vertex()`?**
`hit_flash.gdshader` has only `fragment()` (line 7), which runs once for every pixel. `brick_surface.gdshader` has `vertex()` (line 17) and `fragment()` (line 22). If the colour line moved into `vertex()`, the tank would be multiplied by red instead of mixed with red.

**3. Three built-ins you read, two you wrote; which of the ones you read are read-only?**
I read `COLOR` (`hit_flash.gdshader` line 8), `VERTEX` and `NORMAL` (`brick_surface.gdshader` lines 18–19), and `UV` (`hint_experiment.gdshader` line 10). I wrote `COLOR`, `ALBEDO` (`brick_surface.gdshader` line 33) and `ROUGHNESS` (line 34). `UV` inside `fragment()` is read-only.

**4. Does each hint change only the Inspector, or also the value the shader receives?**
`hint_range` (`hit_flash.gdshader` lines 3 and 5) only affects the Inspector. `source_color` on a sampler (`hint_experiment.gdshader` line 4) changes the value the shader receives: in my hint experiment the same file value 64 shows as 64 through the sampler with `source_color`, but as 137 through the sampler without it (line 5).

**5. Does `hint_range` clamp a value set from code?**
No. I set `hit_amount` to 2.0 and both pixels became pure red (255, 0, 0), which shows it was not limited to 1. See `hit_flash.gdshader` line 3 and `docs/a5/captures/hit_flash_2.0.png`.

**6. Which line of the generated shader makes the albedo sample as colour and the normal map as data, and what is the equivalent in your textured shader?**
In the generated shader, line 7 gives the albedo `source_color`, so it is read as colour; line 19 gives the normal map no `source_color`, so it is read as data. In my brick shader, line 4 is the colour equivalent and line 9 is the data equivalent.

**7. Why can't `fragment()` read what the neighbouring pixel's `fragment()` is computing, and how does game state reach it?**
The GPU computes pixels in parallel, with no order between them, and each call is independent of the others, so a pixel cannot read its neighbour's result. Game state is passed in as a uniform: every frame the driver calls `set_shader_parameter` to set the uniform on line 3 of `hit_flash.gdshader`.

**8. Two things the Godot shading language provides that plain GLSL does not.**
One is uniform hints, for example `hint_range` (`hit_flash.gdshader` line 3), which automatically creates a slider in the Inspector. The other is built-in outputs such as `ALBEDO` and `ROUGHNESS` (`brick_surface.gdshader` lines 33–34), which Godot connects to its PBR lighting automatically.
